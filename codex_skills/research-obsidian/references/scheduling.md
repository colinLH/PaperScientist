# 创建和运行定时任务

先完成初始化及 doctor，确认运行环境能访问本地 Obsidian 仓库。
查找当前 `automation_update` 工具并读取其最新 schema；不要凭本文猜测参数，也不要写 cron、launchd 或 automation.toml 来替代用户要求的 Codex 定时任务。
没有自动化工具时提供可复制提示词并明确“未创建日程”，不声称定时任务已经启用。

先检查现有 automation.toml 或当前工具提供的任务列表，按 skill 名、配置绝对路径和工作模式匹配。
优先更新同一配置的任务，不修改其他人的任务或仅同名的其他仓库任务。
只有在用户要求迁移既有任务时才更新，保留原任务 ID、时刻、模型和通知偏好。旧名称的迁移见 compatibility.md。

用户请求设置本工作流时，默认建议两项：配置时区每天 collect_at 收集，sync_at 同步。任务名称包含实际 domain.name，例如「<领域>论文日报 → Obsidian」和「同步 Obsidian <领域>知识图谱」，同名领域的多个实例再加专区名以区分。
遵循宿主工具约定选择 heartbeat；用户明确要求每轮独立任务或独立项目作业时才选择 cron，并先通过 list_projects 取得真实 projectId。
不要硬编码模型、项目 ID 或别人的 threadId。如果工具必需模型字段，使用用户当前配置的有效模型。
时区按工具实际语义处理：若它只支持宿主本地时区，核对配置时区和宿主时区；不相同且无法明确表达时，说明限制并取得有效日程，不静默把本地时间当 UTC。

运行以下命令取得包含配置路径的提示词：

```text
<PYTHON> <SKILL>/scripts/workflow.py --config <CONFIG> prompts
```

输出的 `prompts.collect` / `prompts.sync` 分别放入两项任务。
如果用户只想创建一个定时任务，使用 `prompts.daily`，每轮先归档再同步。
这些提示词明确禁止运行中再次创建任务；定时轮次始终是执行模式。
保留用户的通知偏好，默认无变化时安静，仅有实际变化、失败或需处理的问题时通知。

通过 automation 工具实际写入后，读取或核对返回的 ID、启用状态、执行时间和提示词。
将成功登记的 ID 和模式记录到 `<WORKSPACE>/automations.json`，仅作为本地回执；这个文件不是调度器。
只有工具确认成功才向用户说“已创建/更新”。单独修改配置时间不会更新日程，需调用自动化工具。
日报09:00、图谱13:00是建议间隔，仍要通过文件锁和完整性检查处理延迟或并发。
